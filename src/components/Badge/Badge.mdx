# Badge

The `Badge` component communicates small pieces of contextual information such as status, category, or metadata.

Badges are designed to support content, not replace it. They should provide quick visual recognition without becoming the primary focus of the interface.

---

## When to use Badge

Use Badge when you need to communicate:

- Status
- Categories
- Labels
- Short metadata
- Informational states

Examples:

- Account status
- Content state
- Feature availability
- Workflow progress

```tsx
<Badge variant="success">
  Active
</Badge>
```

---

## When not to use Badge

Badges should not be used for interactive actions.

Avoid using Badge as:

- A button
- A navigation element
- A filter control
- A clickable tag

For interactive elements, use components designed for user actions instead.

## Semantic Colors

Badge uses Atoria's semantic color system rather than hard-coded colors.

For example:

```tsx
<Badge variant="success">
  Completed
</Badge>
```

maps to the design system's success tokens.

This allows colors to evolve globally while keeping components consistent.

---

## Accessibility

Badge content should remain understandable without relying only on color.

Good:

```tsx
<Badge variant="success">
  Completed
</Badge>
```

Avoid:

```tsx
<Badge variant="success" />
```

Color should reinforce meaning, not communicate information by itself.

---

## Design Philosophy

Badges are intentionally simple components.

They communicate:

> "Here is additional context about this item."

They do not:

- trigger actions
- manage state
- replace buttons
- replace form controls

Keeping this responsibility clear allows Badge to remain predictable and reusable throughout an application.
